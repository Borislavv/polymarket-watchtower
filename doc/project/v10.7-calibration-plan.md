# v10.7 — Calibration Phase Plan (placeholder)

This document is the **planning artefact** for the next phase. v10.6
deliberately stays small: enable WS, no retuning. v10.7 is where we
calibrate. NONE of the items below ship in the v10.6 WS-enable PR.

## Track A — Prompt tightening

Goal: reduce essay-length AI outputs without losing decision content.

1. **Inventory**: pull the longest 50 alert / prediction / intel
   outputs of the last 7 days from `polymarket_alert_analyses`,
   `polymarket_market_intelligence_reports`,
   `polymarket_daily_political_intel_reports`. Identify which surface
   produces the longest median outputs and whether they exceed
   `MaxOutputChars`.
2. **Cap-tightening candidates**:
   - `AI_ANALYSIS_MAX_OUTPUT_CHARS=700` → keep.
   - `AI_MARKET_INTELLIGENCE_MAX_OUTPUT_CHARS=2000` → consider 1500.
   - Daily intel: per-paragraph 1500-2500 → keep but enforce
     paragraph-splitting.
3. **Style rules to bake into prompts**:
   - "Avoid repeating market fields the operator already sees in the
     header."
   - "Make a call. No paragraph of qualifiers."
   - "Cap reasoning paragraphs at 3 sentences."
4. **Validation**: a snapshot test per surface that asserts
   `len(body_excluding_header) ≤ surface_cap`.

## Track B — Alert / prediction efficiency

Goal: measure which strategies produce signal vs noise.

1. **Existing data**:
   - `polymarket_alert_outcomes` (resolved_correct / wrong / pending).
   - `polymarket_prediction_feedback` (per-horizon delta).
   - `polymarket_alert_strategy_dimensions` (per-alert strategy +
     buckets).
   - `polymarket_market_predictions.usefulness_score`.
2. **Query plan**:
   - join alerts × outcomes × strategy_dimensions, compute per-
     (strategy_family, lifecycle_bucket, notional_bucket) success
     rate over the last 30 days.
   - For predictions: compare `usefulness_score` to delta from
     `polymarket_prediction_feedback`.
3. **Output**: a one-shot CLI `go run ./cmd/cli efficiency-report`
   that prints a markdown table + a JSON for ingest.
4. **Action**: each strategy with success-rate < its implied
   probability gets a NOTE entry in `doc/strategies/` and a follow-up
   threshold candidate.

## Track C — Strategy noise reduction

Goal: surface fewer, higher-signal alerts without disabling any
strategy.

1. **Multiplier baseline (PART 9.3 — p99 over p95)**:
   - Move `MultiplierTier` evaluation from `max(market_p95,
     trader_p95)` to `max(market_p99, trader_p99)` where data
     density allows. Requires baseline reservoir to track p99
     explicitly — work item.
2. **Low-liquidity suppression**: today the worker accepts every
   trade into the baseline reservoir. Operator evidence in prod
   shows the bottom quintile of markets (vol24h < $1k) produces
   most of the alert noise. Add a per-market `MIN_VOLUME_24H_USD`
   gate to the alert path; baseline reservoir is unchanged.
3. **Cluster threshold uplift**: bump `CLUSTER_MIN_UNIQUE_TRADERS=3`
   → 4 when total notional crosses $200k. Soft floor; the strict
   threshold stays at 3 for the small-cluster case.
4. **Accumulation lifetime promotion**: only promote `lifetime`
   accumulation alerts to `warning` when total notional > $50k AND
   `LifecyclePct > 80`. Today it can fire on a small lifetime line
   in a young market.
5. **Already-priced demotion**: when `polymarket_repricing_signals.
   repricing_status='already_priced'` is set for the market within
   the last 6 h, demote any single-trade alert one tier.

## Track D — Telegram UX validation

Goal: validate the v10.5 redesign in prod over a 7-day window.

1. **Coverage check**: every Telegram surface should be exercised at
   least once in 7 days. Build a queryable summary from
   `polymarket_alerts.created_at + delivery_status` and the daily
   intel / market intel rows.
2. **Header presence**: golden tests in v10.5 already pin Type /
   Trigger / Strategy / AI. Operator should still spot-check 5 random
   messages per surface and confirm the header reads right on
   mobile.
3. **Event-link guarantee**: every event-specific alert should carry
   the `Polymarket event` link. v10.5 golden tests pin this; the
   operator confirms in prod with a one-line grep over
   `polymarket_alerts.body` (if the body is persisted) or a Telegram
   audit.
4. **No AI essay in title**: v10.5 already gates this at render time
   (Prediction Update title is the STATE only). Validate in
   production by sampling.

## Operational guardrails for v10.7

- Each track is an opt-in CLI / config knob — none ship enabled by
  default until the operator has run the relevant report.
- Threshold changes go through `presets/prod.env.template` first,
  not the code defaults. Code defaults stay conservative.
- Every retune PR includes a `presets/prod.env.template` diff so an
  operator can revert exactly the v10.7 changes by holding the
  v10.6 file.

## When v10.7 is "done"

- Track A: each surface has a documented cap and a snapshot test.
- Track B: a 30-day per-strategy success-rate table is generated
  weekly and reviewed.
- Track C: 5 specific threshold proposals committed to
  `presets/prod.env.template`, each with the per-day alert-volume
  delta documented.
- Track D: an audit-Sunday checklist exists with the v10.5 surfaces
  enumerated.
