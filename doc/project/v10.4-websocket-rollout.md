# v10.4 — Hybrid WebSocket Realtime Fast-Lane Rollout

WebSocket fast-lane = **trigger accelerator**. Polling + backfill remain
the canonical source of truth. WS NEVER calls AI, Telegram, or the
severity layer directly — it persists to `polymarket_ws_events`,
upserts `polymarket_live_market_state`, and enqueues
`polymarket_realtime_work_queue`. The alertsender + AI workers pick
work up through the same paths they used pre-v10.4.

Feature flag: `WS_ENABLED=false` by default. Every phase below assumes
disabling reverts to the polling-only steady state immediately, no
data migration needed.

## Phased rollout

### Phase 0 — Merged, OFF

State: `WS_ENABLED=false`, all WS env knobs documented in
`.env.example` and `presets/prod.env.template`. Migration 00023
applied (4 tables live, empty). Grafana panels 401-413 visible but
flatlined. No goroutines started — verified by `app.go` short-circuit
when `cfg.WS.Enabled=false`.

Exit criteria: production CI green, no behavioural change vs v10.3.

### Phase 1 — CLI smoke on 1-3 markets

State: WS still OFF in production. Operator runs:

```bash
go run ./cmd/cli ws-smoke \
  --tokens <clob_token_id_1>,<clob_token_id_2> \
  --duration 60s
```

What to check:
- Connection establishes (`polymarket ws: subscribed` log line with
  `tokens=N`).
- Event types observed in the summary include at least one of
  `book`, `price_change`, `last_trade_price`, `best_bid_ask`.
- No panics, no goroutine leaks.

Then re-run with `--persist --dsn $POSTGRES_DSN` and verify rows
land in `polymarket_ws_events` and `polymarket_live_market_state` but
NOT in `polymarket_alerts`, `polymarket_telegram_*`, or any AI table.

### Phase 2 — Single-process staging, hot mode

State: `WS_ENABLED=true`, `WS_SUBSCRIPTION_MODE=hot`,
`WS_MAX_MARKETS=25` (tight cap for first prod-like run). Run for ≥1
hour with the full daemon. Watch:

- `watchtower_ws_connected` should stay at 1.
- `watchtower_ws_reconnects_total` should stay flat or grow at most
  a few times.
- `watchtower_ws_events_total{type}` should be non-zero for at least
  `book` and `last_trade_price`.
- `watchtower_ws_events_dropped_total{reason="buffer_full"}` should
  be ~0 at this scale (10k buffer >> 25-market event rate).
- `watchtower_realtime_work_enqueued_total{reason}` should grow,
  primarily `trade_seen` (every trade-like event) and occasionally
  `price_move` / `book_change` (only when the live-state delta
  crosses `WS_PRICE_MOVE_TRIGGER=0.03`).

Exit criteria: no panics, alertsender + AI workers continue producing
alerts at the same rate as Phase 1 (verifying the canonical pipeline
is unaffected by WS being ON).

### Phase 3 — Scale to 100 markets

State: `WS_MAX_MARKETS=100`. Same observability checks. The
PriceMoveTrigger cooldown should keep `realtime_work_enqueued_total`
bounded — if it explodes, raise `WS_REPRICING_TRIGGER_COOLDOWN` from
60s toward 5m.

### Phase 4 — Full prod, 250 markets

State: `WS_MAX_MARKETS=250` (the documented v10.4 default).
Subscription refresh runs every `WS_SUBSCRIPTION_REFRESH_EVERY` (5m
default); the worker re-runs the SQL selector and asks the client
to re-subscribe on the next reconnect.

Exit criteria for "v10.4 in steady state":
- 24h with `watchtower_ws_connected` ≥ 99% uptime.
- 24h with `watchtower_ws_events_dropped_total` rate < 1/min.
- No regression in `watchtower_alerts_sent_total` rate vs Phase 0
  baseline.

### Phase 5 — (Reversible at any time)

If anything goes sideways: `WS_ENABLED=false` + restart.
Polymarket polling + backfill + AI workers keep working unchanged.
The 4 WS tables remain populated up to the cutover moment and can be
inspected / wiped manually — no production query depends on them.

## Performance estimates (informational)

For a 25-market subscription set (Phase 2):

| Quantity | Estimate | Source |
|---|---|---|
| inbound events/sec | 5-20 | book + price_change at quiet times, bursts to ~50 during catalyst minutes |
| DB writes/sec | 5-20 (ws_events) + ≤25 (live_state upserts) | one row per inbound event, one upsert per condition_id |
| realtime_work_queue inserts/sec | < 1 | dedupe collapses bursts to ≥ 1/minute per (condition, reason) |
| memory channel depth | typically 0-10 / max 10,000 | `WS_EVENT_BUFFER=10000` |
| reconnect cadence | rare — Polymarket WS uptime is generally good; expect single-digit reconnects/day per process |

At 250 markets (Phase 4) scale by ~10x. With the documented buffer
size + cooldowns this still sits well below the DB's commit ceiling
(observed >1k INSERT/s on the production pool).

```sql
WHERE received_at > now() - interval '10 minutes'

-- Live-state is being refreshed for the subscribed markets.
SELECT condition_id, mid, last_ws_event_at
FROM polymarket_live_market_state
WHERE last_ws_event_at > now() - interval '5 minutes'
ORDER BY last_ws_event_at DESC

FROM polymarket_realtime_work_queue
WHERE available_at > now() - interval '15 minutes'
GROUP BY reason;
```

## Non-bypass invariants (do NOT relax)

1. `realtime` package does NOT import `internal/infra/telegram`,
   `internal/infra/ai`, `internal/infra/alerting`, or any other
   downstream surface. Pinned by `architecture_test.go`.
2. Every WS-side trade is persisted with `side_source='websocket'`
   and `side_confidence=0.5`. The strategy layer remains free to
   downgrade severity when this is the only evidence.
3. The realtime work queue's `dedupe_key` is `condition_id + reason
   + minute_bucket` — bursts collapse to one row per minute.
4. `WS_ENABLED=false` is the safe default. The worker goroutine
   never starts when the flag is off.
